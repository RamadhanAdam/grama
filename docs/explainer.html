GraMa · federated intrusion detection for in-vehicle networks

How GraMa works

A car's computers talk on a bus that trusts every message. GraMa watches that traffic as a graph that changes over time, learns across many cars without collecting their data, and keeps hacked cars from poisoning what everyone learns. Each chapter below runs live; the controls change what you see.

01

Inside the car

A modern car has dozens of small computers called ECUs: one for the engine, one for the brakes, one for the dashboard, and so on. They share one pair of wires, the CAN bus, and every message is heard by every ECU.

A message is tiny: an ID that says what it is about (and sets its priority; a lower ID wins) and up to 8 bytes of data. There is no sender address and no signature. Any device on the bus can send any ID.

The log under the car is what a diagnostic tool would print, in the same format as Linux candump: time, interface, ID in hex, length, then the bytes.

The data: CIC-IoV2024, recorded on a 2019 Ford. The dataset doesn't say which ECU sends which ID, so the pairing in the picture is made up; the IDs are real ones from its benign traffic.

Amber and green: the two wires of the bus (CAN-H and CAN-L). Each dot is one message spreading to every ECU.

02

Attacks on the bus

Anyone who gets a device onto the bus, through the diagnostic (OBD) port or a hacked ECU, can send messages too. CIC-IoV2024 records two kinds of attack.

Denial of service: the attacker floods the bus with a high-priority ID. Real messages keep losing the race for the wire and arrive late or not at all.

Spoofing: the attacker sends believable-looking messages with false values, here a speed, so whichever ECU trusts them acts on a lie. The dataset spoofs gas pedal, RPM, speed and steering-wheel data.

The frames in the log are the real attack frames from the dataset: DoS used ID 0x123 (291), and speed spoofing used 0x158 (344). None of the attack IDs ever appears in the car's normal traffic.

In the code: the six CSV files are read by src/grama/data/build.py; each file's class comes from its name.

03

Windows of traffic

GraMa doesn't judge one message at a time. It cuts the stream into windows of 64 messages, each starting 32 messages after the last, so neighbouring windows overlap by half.

It then reads 8 windows in a row as one sequence: 288 messages, well under a second of traffic on a busy bus. The sequence gets the label of its last window, so the question is always "is this happening now?".

Here the last part of the stream has spoofed frames mixed in (red), so the last windows, and therefore the sequence, count as an attack.

In the code: window_stream() in src/grama/data/build.py; the sizes are in config/data.yaml.

Each thin bar is one message. The bracket is the current window; the boxes below fill as the window slides.

04

Traffic as a graph

Each window becomes a small graph. Every message ID seen in the window is a node, and two IDs are joined by an edge when a message with one is followed directly by a message with the other. In normal driving the same IDs follow each other in the same rhythm, so the graph keeps a familiar shape.

Injected messages break that rhythm. The spoofed ID shows up as a new node wedged between the real ones, with edges to everything around it.

Each node also carries 10 numbers: the average of each of its 8 bytes in this window, its share of the window's messages, and whether it sent more than an average node (a burst). Click a node to see them.

In the code: node features in src/grama/data/build.py, edges in src/grama/data/dataset.py. The real windows have 64 messages; this one shows 16.

    The model

    Graph attention reads each window's graph. Every node looks at its neighbours and decides how much each one matters, then the nodes are combined into one summary of the window. A node with nothing like it in normal traffic stands out.

    Mamba then reads the 8 summaries in order and carries a memory from one to the next, so a change that builds over several windows is noticed. It is a state-space model: like a recurrent network, but built to stay fast on long sequences.

    A small classifier turns the final memory into a verdict: normal, or which attack.

    In the code: src/grama/models/gat_encoder.py, mamba_block.py and classifier_head.py. About 78,000 numbers in total, about 300 KB.

    Learning across cars

    One car sees only its own traffic. To learn from many cars without collecting anyone's driving data, GraMa uses federated learning. Each round, some cars train the detector on their own traffic and send back only the change to the model, their update. The server combines the updates and sends the improved model to every car.

    Cars don't all see the same traffic. One might log mostly normal driving, another happened to be attacked a lot. The slider sets how different they are. Far left, each car sees mostly one kind of traffic; this is the hard case.

    In the experiments there are 20 cars, 10 take part in each round, and training runs for 30 rounds.

    In the code: src/grama/federated/client.py and server.py; the split between cars in src/grama/data/federated_split.py (a Dirichlet split, the standard way to make uneven clients).

    Hacked cars and the defence

    A hacked car can send a poisoned update. The experiments try four ways: label flipping (train on wrong answers), targeted flipping (teach the model that attacks are normal), magnitude poisoning (blow the update up ten times) and ALIE ("a little is enough": a carefully small push that hides inside the honest spread).

    Plain averaging (FedAvg) lets every update in. Norm clipping shrinks oversized ones. FLAME groups updates by direction and clips. GraMa's defence squeezes each update into a small map, finds the dense group of honest cars with HDBSCAN, and drops the ones far from it.

    The picture is a 2D sketch: real updates have about 78,000 numbers each, so the groups overlap far more than here. How much they overlap, and which defence copes best, is what the experiments measure.

    In the code: GraMa's defence in src/grama/federated/aggregator.py; FedAvg, median, trimmed mean, Multi-Krum, norm clipping and FLAME in robust.py; the attacks in src/grama/attacks/poisoning.py.

    What the experiments test

    Five questions, from the concept note's Section 6: does GraMa detect attacks as well as a CNN-BiGRU detector; how much uneven traffic across cars hurts; how each defence holds up as 10 to 40% of cars are hacked; which parts of GraMa matter (an ablation); and how small and fast it is.

    Before any of that, the data needed a close look. Each attack file is a handful of distinct messages repeated in long runs, and the RPM and speed files end with messages on ID 513 that appear nowhere earlier. Testing on the last 20% of each file would put those runs only in the test set, and every model stopped at a macro-F1 of about 0.56. The test set is instead every fifth block of 1,000 messages, so every run of messages is seen in training.

    In the code: src/grama/experiments/runner.py and report.py; the profiles in config/experiments.yaml.
